Local LLM inference — a practical decision guide

vLLM, SGLang & llama.cpp

Three excellent open-source engines for running language models on your own hardware. They aren't really competitors so much as answers to different questions. Here's how to tell which one fits what you're doing.

vLLM

The concurrency workhorse

Production serving built to handle many requests at once. If you're feeding a fleet of users or agents from one box, this is the one that keeps aggregate throughput high.

SGLang

The single-stream speedster

Fastest time-to-first-token and per-request speed, with the strongest structured-output engine. Shines on low-concurrency, latency-sensitive, and heavily-templated workloads.

llama.cpp

Runs anywhere

The portability champion — CPU, Apple Silicon, tiny VRAM, mixed hardware. GGUF quantization fits big models into small memory. The go-to for single-user and edge.

Which one should you pick?

Start here. The right choice is driven almost entirely by your workload and hardware, not by which engine is "best" — all three are genuinely good.

vLLM

Choose it when…

  • You serve many concurrent requests — multiple users, or an agent fleet hitting one endpoint.
  • Aggregate throughput matters more than the speed of any single reply.
  • You have datacenter-class NVIDIA GPUs and want a stable, well-worn production server.
  • You want fast support for brand-new model architectures.

SGLang

Choose it when…

  • You want the fastest possible single response — lowest latency per request.
  • Your work is heavy on structured output (JSON, tool calls, constrained decoding).
  • You reuse long shared prefixes — RadixAttention caches them and pays off big.
  • Concurrency is low-to-moderate, and raw per-stream performance is the goal.

llama.cpp

Choose it when…

  • You're on CPU, a Mac, limited VRAM, or mixed hardware — anything but a big GPU.
  • You need heavy quantization (GGUF) to fit a large model into small memory.
  • It's a single-user, laptop, edge, or embedded setup.
  • You want the simplest possible setup — one binary, one model file, done.

The honest pros & cons

No engine wins everywhere — each buys its strengths with a real trade-off.

vLLM

Strengths

  • Best concurrent throughput of the three
  • Mature, widely-deployed production server
  • Efficient KV memory (PagedAttention)
  • Quick to support new models; big ecosystem
  • Strong multi-GPU tensor parallelism

Trade-offs

  • GPU-only, CUDA-first — no real CPU path
  • Pre-allocates its KV pool, so it's memory-hungry at idle
  • Single-stream latency a touch behind SGLang
  • Heavier to stand up than llama.cpp

SGLang

Strengths

  • Fastest single-request latency and decode
  • RadixAttention reuses shared prefixes — great for agents and repeated system prompts
  • Best structured-output / constrained decoding
  • Excellent for complex, programmatic prompting

Trade-offs

  • GPU-only, CUDA-first
  • Concurrency can be capped on some architectures (notably hybrid-Mamba models)
  • Younger / less ubiquitous than vLLM
  • Some configs are finicky at the edges

llama.cpp

Strengths

  • Runs on almost anything — CPU, Mac, low VRAM, mixed
  • GGUF gives unmatched quantization range to shrink big models
  • Trivial setup — a single binary and a model file
  • Ideal for single-user, laptop, and edge use
  • Very active community, huge model coverage

Trade-offs

  • Weak under concurrency — not a multi-user server
  • Lags on brand-new architectures (GGUF conversion delay)
  • Multi-GPU support is basic
  • CPU speed is bandwidth-bound — fine for one user, not throughput
The one-line version: if you're serving a crowd, reach for vLLM; if you want one answer as fast as possible or lean hard on structured output, reach for SGLang; if you're running on whatever hardware you happen to have — especially without a big GPU — reach for llama.cpp. Many good setups use more than one: a GPU serving engine for the main workload and llama.cpp as a CPU fallback or for a second model on constrained hardware.

Reflects hands-on testing of all three on the same models and hardware. Specifics (exact speeds, per-architecture quirks, feature support) shift with each release — treat the decision framework as durable and re-benchmark the numbers for your own setup and model.
